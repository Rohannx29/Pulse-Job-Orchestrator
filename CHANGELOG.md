# Phase 1 — Correctness Gaps — Complete

All five P0 items from the backlog were live-verified against real **PostgreSQL + Redis + Celery**, rather than only being unit-tested in isolation.

## Added

### Redis-backed queue concurrency

Added `app/concurrency.py`, implementing a Redis-backed atomic counting semaphore for enforcing `Queue.concurrency_limit` on a per-queue basis.

**Verification:**

- 3 simultaneous jobs were submitted to a queue with `concurrency_limit=1`.
- The worker fleet had 6 available execution slots.
- Jobs still executed strictly sequentially.
- No execution windows overlapped.

### Priority-based worker isolation

Added `app/priority.py`, which maps `Job.priority` to three dedicated Celery queues:

```text
pulse.high
pulse.normal
pulse.low
```

Updated `docker-compose.yml` to run a dedicated worker pool for each priority tier, plus `worker-internal` for housekeeping tasks.

This makes priority a real capacity-isolation mechanism rather than a cosmetic database field.

**Verification:**

- Priority-2 job executed only on `worker-high`.
- Priority-9 job executed only on `worker-low`.
- No cross-tier execution leakage was observed.

### Job handler registry

Added the `HANDLERS` registry in `app/tasks.py`, keyed by:

```python
payload["type"]
```

The existing `simulate` handler remains available for deterministic testing.

Added a real `http_request` handler and verified it against a live request to:

```text
api.github.com
```

### Alembic migrations

Added schema migrations under:

```text
backend/alembic/
```

The initial migration was autogenerated from the existing models and covered all 12 entities.

### Queue pause execution control

Queue pause was changed so that it stops execution of jobs already dispatched to Celery, rather than only preventing new job creation.

`execute_job` now checks `queue.is_paused` and defers execution through `self.retry()` without modifying the job's own retry count.

**Verification:**

A delayed job remained in `scheduled` status for approximately 8 seconds beyond its ETA while the queue was paused, then completed a few seconds after the queue was resumed.

## Fixed

### Idempotency key returned 500 on duplicate requests

**Problem**

Duplicate requests previously raised a raw database `IntegrityError` instead of returning the existing job.

**Fix**

`create_job` now:

1. checks for an existing job using `(queue_id, idempotency_key)`;
2. returns the existing job with HTTP `200` when found;
3. catches `IntegrityError` as a race-safe fallback when two requests arrive nearly simultaneously.

This turns the database uniqueness constraint into an actual idempotent API behavior.

### Alembic downgrade did not remove PostgreSQL ENUM types

**Problem**

The initial migration's `downgrade()` removed the tables but not the PostgreSQL-native ENUM types:

```text
workerstatus
jobstatus
retrystrategy
loglevel
```

`op.drop_table()` does not automatically remove a separately-created named enum.

A complete:

```text
upgrade → downgrade → upgrade
```

round trip therefore failed on the second upgrade with `DuplicateObject`.

**Fix**

Added explicit:

```python
sa.Enum(name=...).drop(bind, checkfirst=True)
```

calls to the downgrade path.

**Verification**

The complete migration round trip was re-run successfully.

# Phase 2 — Reliability & Operations — In Progress

## Added

### Job workflow dependencies

Added:

```text
Job.depends_on_job_id
```

as a self-referential foreign key and introduced the:

```text
BLOCKED
```

job status.

A job with an unmet dependency is written directly to `BLOCKED` and is never dispatched to Celery.

`app/tasks.py::_release_dependents()` dispatches blocked dependents when their parent completes.

`_cascade_fail_dependents()` recursively dead-letters dependents when their parent permanently fails, preventing a dependency chain from remaining blocked forever.

**Verification — success path**

A real:

```text
A → B → C
```

chain executed in strict order with zero overlap.

`B` started approximately 83 ms after `A` finished; the observed delay was release latency rather than a race.

**Verification — failure path**

A real:

```text
X → Y → Z
```

chain where `X` always failed propagated DLQ status through all three jobs.

Each `DeadLetterJob.reason` remained traceable to the preceding failure.

### Shared dispatch module

Added:

```text
app/dispatch.py
```

and extracted job-to-Celery dispatch into one shared function.

The common dispatch path is used by:

- job creation;
- dependent release;
- cron dispatch.

This avoids maintaining multiple copies of priority routing and dispatch behavior that could drift apart.

### Dependency tests

Added:

```text
tests/test_dependencies.py
```

with three integration tests using real PostgreSQL while mocking Celery dispatch.

## Fixed

### Alembic failed to detect the `BLOCKED` ENUM member

**Problem**

Alembic autogenerate did not detect the addition of the new `BLOCKED` member to the existing PostgreSQL `jobstatus` ENUM.

Autogenerate compares table/column structure but does not automatically generate new members for an existing PostgreSQL ENUM.

**Fix**

Added an explicit:

```sql
ALTER TYPE jobstatus ADD VALUE IF NOT EXISTS 'BLOCKED'
```

migration.

The first attempt used:

```text
blocked
```

instead of:

```text
BLOCKED
```

because SQLAlchemy stores the Python enum member's name in this schema.

**Verification**

The issue was caught using:

```text
enum_range()
```

against the live PostgreSQL column, corrected, and re-verified.

### Dispatch-before-commit race

**Problem**

A pre-existing race existed in:

```text
create_job
create_jobs_batch
retry_job
```

where the job was handed to Celery **before** its PostgreSQL row was committed.

Theoretical failure sequence:

```text
API creates job
    ↓
Celery task dispatched
    ↓
worker receives task
    ↓
worker queries PostgreSQL
    ↓
job row is not committed/visible yet
    ↓
execute_job silently finds nothing
```

This could result in a job accepted by the API but never actually executed, without an error being surfaced.

**Fix**

Changed the ordering to:

```text
commit job
    ↓
dispatch to Celery
    ↓
commit any resulting status change
```

Applied consistently across all dispatch call sites, including:

- ordinary job creation;
- batch creation;
- manual retry;
- dependent release;
- cron dispatch.

## Fixed — Security

### Schedule toggle had no authorization check

**Problem**

`POST /schedules/{id}/toggle` looked up a schedule only by ID and did not verify ownership.

Any authenticated user who knew or guessed another organization's schedule UUID could therefore toggle that schedule.

**Fix**

Added:

```text
_get_owned_schedule()
```

following the existing organization-ownership validation pattern.

**Verification**

- Cross-organization request → `404`
- Same-organization owner → succeeds

### `http_request` handler was an open SSRF surface

**Problem**

The handler previously accepted arbitrary target URLs.

A caller could potentially target:

```text
169.254.169.254
127.0.0.1
private/internal services
```

from inside the worker network.

**Fix**

Added:

```text
app/url_safety.py
```

with:

- private-address blocking;
- loopback blocking;
- link-local blocking;
- reserved-address blocking;
- HTTP method allowlist;
- timeout cap;
- streamed response-size cap;
- explicit `follow_redirects=False`.

**Verification**

A request to the cloud metadata endpoint:

```text
169.254.169.254
```

was blocked with a clean error and sent to the DLQ.

Legitimate external requests continued to succeed.

## Fixed — Correctness & Reliability

### DLQ manual retry left a stale `DeadLetterJob`

**Problem**

Manual retry reset the job's retry count and re-dispatched it but left its existing `DeadLetterJob` row.

If the job failed again, inserting another DLQ row could violate the unique `job_id` constraint.

**Fix**

Manual retry now removes the existing DLQ state before re-dispatch.

**Verification**

The same job was taken through three complete:

```text
fail → DLQ → retry → fail → DLQ
```

cycles with zero crashes.

### Worker / `CLAIMED` state existed only in the schema

**Problem**

The following existed in the schema but were not populated by execution:

```text
Job.claimed_by_worker_id
JobExecution.worker_id
JobStatus.CLAIMED
```

Jobs effectively moved:

```text
queued → running
```

without persistent worker ownership.

**Fix**

Added:

```text
app/worker_registry.py
```

with shared get-or-create behavior used by both execution and heartbeat synchronization.

`execute_job` now records:

```text
queued
  ↓
claimed
  ↓
running
```

with the actual worker stored on both the Job and JobExecution records.

Added:

```text
GET /workers/{id}/jobs
```

for querying jobs associated with a worker.

**Verification**

A real in-flight job populated:

```text
Job.claimed_by_worker_id
JobExecution.worker_id
```

with a real worker row.

The claim was cleared after completion.

### `Queue.priority` and `Job.priority` had no defined relationship

**Problem**

Both fields existed, but only `Job.priority` affected routing.

`Queue.priority` therefore had no effective behavior.

**Fix**

Made `Job.priority` optional at creation:

```text
None
    → inherit Queue.priority

explicit value
    → override Queue.priority
```

The effective priority is resolved at creation time.

Applied consistently to:

- single job creation;
- batch creation;
- recurring schedule creation.

**Verification**

A queue created with:

```text
priority = 2
```

produced:

```text
job without explicit priority → 2
job with explicit priority 9  → 9
```

### Concurrency semaphore had a shared-TTL edge case

**Problem**

The original semaphore used a single Redis counter with a shared TTL.

A long-running job could outlive the counter TTL, allowing another job to acquire a slot even though the first job had not released it.

A late release could also affect another job's count after the original lease had expired.

**Fix**

Rewrote the semaphore as ownership-aware leases using a Redis sorted set:

```text
unique lease token → expiry timestamp
```

Each acquisition has its own expiry and can only release its own token.

Expired leases stop counting automatically after worker failure.

**Verification**

Verified with:

- real concurrent load;
- `concurrency_limit=1`;
- a real lease-expiry test using actual sleep rather than mocked time.

### Cron dispatch had no overlap guard

**Problem**

Celery Beat invokes `dispatch_due_schedules` every 30 seconds.

If one invocation took longer than that interval, a second invocation could begin while the first was still running and both could observe the same schedule as due.

**Fix**

Added a Redis lock around the whole dispatch function:

```text
SET NX EX 25
```

The 25-second expiry is shorter than the 30-second Beat interval so a crashed invocation cannot permanently hold the lock.

## Documented — No Code Change

### Worker visibility is intentionally global

Workers are shared infrastructure.

Any worker can execute jobs belonging to any organization.

Therefore:

```text
GET /workers
```

is intentionally global.

However, worker **job data** remains organization-scoped.

The worker process's existence and hostname are treated as operational infrastructure information rather than tenant-sensitive job data.

If true per-tenant worker isolation were required, the architecture would need dedicated organization-level Celery queues and worker pools.

### Execution semantics are at-least-once

Pulse provides **at-least-once execution**, not exactly-once execution.

A worker crash after an external side effect but before task acknowledgement can cause Celery to redeliver the task and repeat that side effect.

Therefore:

- Pulse's `idempotency_key` provides submission idempotency;
- it does not make arbitrary execution side effects idempotent;
- handlers interacting with external systems are responsible for downstream idempotency where required.

# Engineering Lessons Captured by the Changelog

The changes above reflect several recurring engineering lessons:

1. **A database constraint is not automatically an API feature.**  
   Idempotency requires correct duplicate-request behavior, not just a unique index.

2. **Generated migrations must be executed and tested.**  
   PostgreSQL ENUMs are a particular case where autogeneration has important limitations.

3. **Distributed ordering matters.**  
   Commit-before-dispatch prevents workers from observing state that has not become durable yet.

4. **Worker capacity and logical queue capacity are different concepts.**  
   Celery worker concurrency cannot enforce a Pulse queue's concurrency contract.

5. **Retries, scheduling, and DLQ are state-machine behavior.**  
   They need explicit transitions and operational semantics rather than being treated as incidental task settings.

6. **Mocks cannot prove database integration.**  
   The missing refresh-token migration demonstrated why real PostgreSQL integration tests are necessary.

7. **Security boundaries must be designed around actual network behavior.**  
   The HTTP handler required explicit SSRF protections rather than assuming a caller-provided URL was safe.

8. **Documentation should distinguish verified behavior from intended behavior.**  
   Features and guarantees should only be described as implemented when they have been validated against the actual system.
